12.RDMA存储结构/存储开销

1.Queue buffer​

  1. 用途：传递WRWC控制信息，存储队列（队列中包含WQE）

1. buffer结构​

  • buffer的用途：暂存数据

    • queue buffer：存储WQE
      • CQ、SQ、RQ、SRQ

  • queue buffer的用途：软硬件传递任务信息的媒介

    • 读取和填写操作异步
      • 读取：硬件
      • 填写：用户

  • queue buffer的结构：ring，维护头指针、尾指针；存储对应队列的WQE；通过头尾指针交替计算：线性->环形

  • 如何访问Queue buffer：

    • 软件在内存申请存储空间，作为queue buffer，获取地址交给硬件，硬件可以访问。
    • 用户态驱动：create Qp时申请存储空间，将buffer的存储地址和长度写入QPC。

2. 创建流程【控制路径】​

  • 用户态：
    • 用户调用create QP API —— rdma-core的API简单处理
      • 指定QP类型、
      • 指定QP深度等信息
    • 用户态驱动申请buffer
      • 校验参数
      • 根据 深度x WQE大小 申请buffer（malloc）
        • 页对齐：地址都是系统页面大小的整数倍（系统页：4k，64k）
        • 需要使用其他申请内存的接口，保证页对齐（mmap等，malloc/calloc不行）
      • 完成其他软件资源初始化——通过系统调用陷入内核
  • 内核态：
    • 获取buffer信息
      • 用户态传入：buffer相关信息+起始虚拟地址
    • 为虚拟页面映射物理页，并固定虚拟页和物理页间的关系（pin）：
      • 获取物理页
      • pin住这个物理页（）
    • 获取物理页DMA地址【ib_umem_get()，得到的是一堆buffer集合】
      • 通过DMA接口获取DMA地址【硬件拿到这个地址就可以实现直接访问内存QP buffer】
        • 如果支持IOMMU/SMMU：返回IOVA
        • 否则：PA
      • 通过ib_umem_get() 得到的结果存储在ib_umem（即Infiniband Userspace Memory）结构体
        • 用户Buffer的长度、
        • 起始虚拟地址、
        • 访问权限、
        • 关联的IB设备、
        • 内存信息、
        • 刚刚获取到的一组地址离散的Buffer组成的列表scatterlist table：sg_table
          • 存储scatterlist：描述内存块的数据结构
            • 指向buffer的虚拟地址
            • 长度
            • DMA地址
            • 所在的物理页
            • 页内偏移
    • 内核驱动：组织物理DMA地址供硬件访问
      • 拿到buffer集合，存储的是CPU视角可以访问到的buffer，是VA
      • 开辟新内存，将buffer的物理首地址/DMA地址和长度存储下来，将这块内存的DMA地址交给硬件QPC

3. 使用流程【数据路径】​

  • 用户态：
    • 用户调用POST send API —— rdma-core的API简单处理
      • 下发WR，指定操作类型、
      • 指定Payload的虚拟地址、和一些控制信息
    • 用户态驱动将WR转化为WQE写入QP Buffer
      • 找到应该存放的位置（va+个数*WQE大小）
      • 按照格式配置WQE内容
    • 驱动敲Doorbell【中断：携带QPN和头指针位置】
      • 头指针：指向下一个WQE应该存放的位置
  • 硬件：
    • 解析doorbell：拿出QPN和头指针
    • 从QPC获取QP buffer：
      • 根据QPN找到对应的QPC
      • 通过QPC获取QP buffer的位置，获取WQE存放的位置：DMA地址
        • buffer基地址(DMA地址)+buffer长度，通过指针，获取WQE的DMA地址
    • 获取并解析WQE：
      • 取出WQE
      • 根据约定，解析WQE内容，根据QPC内容，组装完整数据包。

2.MR buffer​

  1. 用途：传递数据（payload）的通道，存储收发的数据

1. MR buffer简介​

1）MR设计的原因​

  1. 需要可以用用户提供的va访问用户发/收的数据
  2. 需要控制访问内存的权限
  3. 保证访问的页面不被换出，网卡可以一直访问，锁页

2）MR相关地址转换​

  1. 虚拟地址转换表：va——pa
    1. 为了减少存储开销，固定页大小，只需要记录每页的首地址
    2. 虚拟存储连续，只需要记住起始的va
    3. 获取到va之后：
      1. va-va_start / page_size = 页号，找到对应映射的pa；
      2. va-va_start % page_size = 页内偏移，找到对应页内位置
  2. 这个映射关系（页表）需要每次注册MR创建
  3. 硬件缓存MTT

3）MR上下文信息​

  1. 类似QPC/CPC/SRQC，一个表，存储MR相关信息
    1. PD、起始VA、长度、L_Key、R_Key、权限以及页表的相关信息等

4）MR实体​

  1. 用户：可被HCA访问的虚拟地址连续的存储空间
  2. 硬件/用户：包含MRC+页表+若干分散的可供存储的页面

2. 注册流程【控制路径】​

1）用户态​

  • 应用程序申请内存

    • 用户申请所需的buffer，根据长度，malloc/calloc【用户提供va和长度给用户态驱动】

  • 应用调用verbs：ibv_reg_mr【创建多个sge时，另外创建映射表】

    • struct ibv_mr *ibv_reg_mr(struct ibv_pd *pd, void *addr, size_t length, int access);

      /*
      pd：MR关联的PD指针
      addr：起始虚拟地址
      length：MR长度
      access：MR的本地和远端访问权限
      */

      // 返回MR指针
      struct ibv_mr {
          struct ibv_context *context; //进程上下文指针
          struct ibv_pd   *pd; //关联的PD指针
          void  *addr; //实际起始虚拟地址
          size_t length; //实际长度
          uint32_t handle; //内核态用于索引资源的句柄，用户不用关注
          uint32_t lkey; //L_Key
          uint32_t rkey; //R_Key
      };

    • 逻辑操作：

  • 用户态驱动

    • 调用verbs之后，rdma-core调用设备注册回调，进入用户态驱动

2）内核态​

  • 获取Buffer信息
    • RDMA子系统进行系统调用
    • 调用厂商内核驱动注册的回调函数
  • 虚拟页映射物理页，固定虚拟页-物理页关系（pin）
    • 调用ib_umem_get()
    • 分配物理页（页对齐）
      • queuebuffer：进入内核态时才申请对应的物理页
      • MR buffer：在申请之前用户就已经在用，可能已经分配好了物理页，只需要pin
    • 申请物理页是否页对齐
      • queue buffer：用户态驱动申请的，页对齐
      • mr buffer：用户自己申请，起始地址，长度大概率不是页对齐的
      • 页对齐的好处：可以少申请一些物理页资源，好管理，访问速度快
  • 获取物理页DMA地址
    • 通过操作系统提供的接口获取物理页DMA地址（PA/IOVA）
  • 组织物理内存页的DMA地址以供硬件访问
    • 拿到页表的DMA地址，获取物理存储的DMA地址
    • 多级页表or一级页表
  • 产生L_Key，R_Key（本端和对端对本地MR的访问权限）
    • key 32bit：24位index，8位key
      • index：MR的唯一编号，由驱动或固件分配（唯一的，用于查找）
      • key：用于校验，驱动生成随机值
    • 生成L_Key和R_Key给用户，写入MRC key值。访问时用于对比。
  • 填写MRC
    • 将控制信息收集准备好后，通过通道下发给硬件写到MRC表项（如何写入表项？）
      • 页表的信息、MR的起始虚拟地址、长度、key和权限等
  • 返回MR信息给用户
    • 将MR返回给用户

3. 使用流程【数据路径】​

1）write​

已经创建好QP，注册好MR

  • 准备数据

    • 将要发送的数据写入本地内存（MR注册前后都也可以）

  • 下发WR

    • 用户调用ibv_post_write()下发WR【WR指明一个sgelist，表明数据在/需要写入这个地址】

    • 请求中相关MR信息

      struct ibv_send_wr {
          struct ibv_sge         *sg_list;
          int                     num_sge;
          union {
              struct {
                  uint64_t        remote_addr;
                  uint32_t        rkey;
              } rdma;
          } wr;
          ……
              
      // 每个ibv_sge指向虚拟内存的一个buffer
      struct ibv_sge {
           uint64_t        addr;    //Buffer的起始虚拟地址
           uint32_t        length;  //Buffer的长度
           uint32_t        lkey;    //MR的L_Key
      };
      • 本端buffer：sglist：存储数据散列表（虚拟地址），可以指向不同MR；num_sge：散列表中的元素个数。
      • 对端buffer：只有对端的一组va，R_Key，通过建连获取信息。

    • 驱动程序将WR转化为WQE填入SQ，并敲Doorbell

      • WQE：指明操作类型+数据存放位置+远端信息等

  • HCA解析WQE

    • 根据doorbell找到对应QPN，获取对应WQE的index；根据QPC记录的QP buffer DMA地址信息获取WQE的地址。
    • 取出WQE，解析控制信息+数据存放位置
      • 根据lkey高24位确定MRC，对比L_Key和MRC中的key确认权限
      • 从MRC拿到MR的base_addr（DMA地址）找到对应的页表（sgelist）拿到va，和MRC的start_va作差求偏移
      • 然后根据偏移找到物理地址PA（先找页号，再找页内偏移）

  • 组装并发送消息

    • 找到数据之后，记录pa和length，在真正发包的时候将数据拷贝到硬件

    • 构造包头：RETH记录：目的地址，R_Key，length

    • 经过物理链路传输数据

  • 接收方接收并解析报文

    • 解析校验【需要remote write权限】
    • 根据R_Key高24bit获取MRC index，找到MRC验证key和低8位是否一致
    • 拿取MRC，获取MR的虚拟地址的首地址，和数据包RETH指定的va计算偏移，找到物理地址PA

  • 将Payload写入内存

    • 将包头拆解，读取payload，通过DMA引擎将payload写入目的内存

  • 回复ack，产生CQE……

2）read​

  • 请求下发WQE（包含多个sge list）
  • 请求返回后，写入WQE指定的sge list

3）send​

  • 需要接收方现在发RQ WQE（包含多个sge list）
  • 接收方收到报文，取出WQE接收数据
    • 根据WQE的sge中的数据来校验权限，指定写入va
    • 【只需要local write】
    • 可以写入多个离散的虚拟地址（sge list）

4.内核如何pin住内存​

  1. 用户驱动申请内存
  2. 内核申请物理页，建立虚拟地址到物理页的转换，将虚拟地址映射到物理页。锁定物理页保证不被换出
    1. 增加引用计数
      1. 管理物理页使用状态的核心机制【引用计数】
      2. 每个物理页有描述该页的struct结构体，当申请该物理页时，会给物理页结构体对应字段计数++
    2. 标记为不可换出页
  3. 内存物理空间连续
    1. scatter-gather
  4. 设备地址注册
    1. 将物理首地址传输给RDMA驱动
  5. 内存进行生命周期管理
    1. 释放页引用计数减少
