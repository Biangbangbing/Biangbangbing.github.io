2. RDMA基础篇-2 基本元素

为了方便，RDMA中有很多概念和操作经常使用缩写代替，本文尽可能记录RDMA所有相关名词缩写及其含义。

缩略语全称含义
WQWork Queue工作队列
WQEWork Queue Entry/Element工作队列元素
QPQueue Pair队列对
SQSend Queue发送队列
RQReceive Queue接收队列
CQCompletion Queue完成队列
CQECompletion Queue Entry/Element完成队列元素
WRWork Request工作请求
WCWork Completion工作完成
MRMemory Region应用专用于RDMA的内存区域
HCAHost Channel Adapter宿主通道适配器，RDMA网卡
MTTMemory Transition Table本地内存VA-PA的映射表

1. WQ​

WQ，Work Queue，存储工作请求的队列，队内放入的元素是WQE，软件下发WQE，将WQE添加到WQ（Post过程），硬件从队列中取出WQE。WQ有若干种，SQ，RQ，CQ等等。

2. WQE​

WQE，Work Queue Entry/Element，工作请求，由软件下发给硬件，包含任务的详细信息（任务类型是SEND，WRITE，READ，RECV，可以访问存储空间的地址，数据长度，对端ip地址等信息），硬件从WQ获取到WQE，根据信息组装数据包进行发送。

3. QP​

QP，Queue Pair，一对WQ，特指SQ和RQ（eg：发送端的Send Queue和Receive Queue）。QP是RDMA中通信的基本单元，每个节点的每个进程可以使用若干个QP（一个进程可以通过不同QP给不同远端QP发送消息），每个QP可以关联一个远端QP，进行消息的传输。每个节点的每个QP拥有唯一编号，称为QPN（Queue Pair Number），可以唯一确定一个节点的QP。

QP是队列结构，按顺序存储WQE（WQE：发送请求任务：目的地址，原地址，数据长度）。一个用户节点可以拥有若干个QP，一个QP只能被一个节点拥有，是用户的独占资源，每个QP相互独立。

  1. QP实体
    1. 存储空间（硬件网卡）：存储若干WQE（内存或者网卡都有实现）
    2. 数据结构（软件驱动）：包含QP地址指针，相关属性。
  2. QPN
    1. 每个QP的编号，24bit，每个节点最多拥有2^24个QP。
    2. 每个节点维护自身的QPN集合，每个节点的QP序列号都是各自的一套。从0开始-（节点指主机网卡，同一HCA上的所有QP（无论绑定到哪个端口或由哪个进程创建）必须具有唯一的QPN，以确保网卡能正确路由请求。）
    3. 编号为0的QP用于子网管理接口SMI（Subnet Management Interface），用于管理子网中的全部节点。
    4. 编号为1的QP用于通用服务接口GSI（General Service Interface），GSI是一组管理服务，其中最出名的就是CM（Communication Management），是一种在通信双方节点正式建立连接之前用来交换必须信息的一种方式。
    5. 当QP被销毁之后，它的QPN也会被重新回收，并在合适的时候分配给其他新创建的QP。

1.QPC：​

Queue Pair Context，用于存储QP相关属性。主要用于硬件，由网卡和配套的驱动程序约定QPC包含的内容、大小、按照什么顺序存放。

  1. 包含内容
    1. MTT表：VA-PA转换表
    2. SQ VA，SQ size
    3. RQ VA，RQ size
    4. ……
  2. 相关上下文：
    1. Device Context，SRQC，CQC，EQC（Event Queue Context，事件队列上下文）等，Device Context，SRQC，CQC，EQC（Event Queue Context，事件队列上下文）等

2.QP控制面（配置资源）​

  1. Create QP：创建QP的软硬件资源（QP，QPC），
    1. 传入属性：服务类型，WQE数量
  2. Destroy QP：销毁QP，释放QP的全部软硬件资源，销毁后无法通过QPN索引到QP。
  3. Modify QP：修改QP属性，修改数据结构和QPC。
  4. Query QP：查询QP状态和属性。

3.QP数据面（数据收发）​

  1. 发起方发起请求：post send request（send操作、write、read操作），向SQ填写WQE
  2. 响应方发起请求：post receive request（receive操作），准备缓冲区，向RQ填写WQE，指明接收的数据存储的位置。

4.QP状态机​

  1. RST（Reset）

    复位状态。当一个QP通过Create QP创建好之后就处于这个状态，相关的资源都已经申请好了，但是这个QP目前什么都做不了，其无法接收用户下发的WQE，也无法接受对端某个QP的消息。

  2. INIT（Initialized）

    已初始化状态。这个状态下，用户可以通过Post Receive给这个QP下发Receive WR，但是接收到的消息并不会被处理，会被静默丢弃；如果用户下发了一个Post Send的WR，则会报错。

  3. RTR（Ready to Receive）

    准备接收状态。在INIT状态的基础上，RQ可以正常工作，即对于接收到的消息，可以按照其中WQE的指示搬移数据到指定内存位置。此状态下SQ仍然不能工作。

  4. RTS（Ready to Send）

    准备发送状态。在RTR基础上，SQ可以正常工作，即用户可以进行Post Send，并且硬件也会根据SQ的内容将数据发送出去。进入该状态前，QP必须已于对端建立好链接。

  5. SQD（Send Queue Drain）

    SQ排空状态。顾名思义，该状态会将SQ队列中现存的未处理的WQE全部处理掉，这个时候用户还可以下发新的WQE下来，但是这些WQE要等到旧的WQE全处理之后才会被处理。

  6. SQEr（Send Queue Error）

    SQ错误状态。当某个Send WR发生完成错误（即硬件通过CQE告知驱动发生的错误）时，会导致QP进入此状态。

  7. ERR（Error）

    即错误状态。其他状态如果发生了错误，都可能进入该状态。Error状态时，QP会停止处理WQE，已经处理到一半的WQE也会停止。上层需要在修复错误后再将QP重新切换到RST的初始状态。

4. SQ、RQ、CQ、SRQ​

SQ，Send Queue，发送队列，存放发送任务，依靠发送方应用层post WQE 到Send Queue；

RQ，Receive Queue，接收队列，存放接受任务，接收方应用层post WQE到Receive Queue；

CQ，Completion Queue，完成队列。队内存储的是CQE（Completion Queue Entry/Element），与WQE相对，WQE是应用通知硬件接收或发送数据，CQE是硬件完成任务告诉应用任务结束（其中包含任务详情，描述哪些任务正确执行，哪些任务执行错误遇到什么错误）

SRQ，Shared Receive Queue，共享接收队列，几个QP共享同一个RQ。使用RQ的情况要远远小于使用SQ，而每个队列都是要消耗内存资源的。当我们需要使用大量的QP时，可以通过SRQ来节省内存。

三者交互过程如下：（可靠传输）

  1. 双端进行握手交互。
  2. 接收端APP以WQE的形式下发一次RECV任务到RQ。
  3. 发送端APP以WQE的形式下发一次SEND任务到SQ。
  4. 发送端硬件从SQ中拿到任务，从内存中拿到待发送数据，组装数据包。
  5. 发送端网卡将数据包通过物理链路发送给接收端网卡。
  6. 接收端收到数据，进行校验后回复ACK报文给发送端。
  7. 接收端硬件从RQ中取出一个任务书（WQE）。
  8. 接收端硬件将数据放到WQE中指定的位置，然后生成“报告”CQE，放置到CQ中。
  9. 接收端APP取得任务完成信息。
  10. 发送端网卡收到ACK后，生成CQE，放置到CQ中。
  11. 发送端APP取得任务完成信息。

1. CQ/CQE​

1.基础概念​

  1. CQE内容：QP指定的某个任务（QPN，WRID），操作类型，执行结果（状态 and 错误码）

  2. CQE作用：硬件向CQ写入CQE

    1. 取出数据：在收到CQE之前，内存区域仍旧在使用中，不能释放相关资源。
    2. 存放数据：获取到CQE并确认其内容之后才能认为消息收发任务已经完成。收到CQE之前，内存区域的东西不一定写完了。

  3. CQE什么时候产生：

    1. RC【可靠服务：本端发出消息对端准确接收】
      1. send：A->B，B收到数据包校验后产生并回复ack，A收到B的ack之后生成本端的CQE。
      2. receive：B收到数据将数据放到用户WQE指定的内存区域，进行校验和数据存放，硬件产生CQE。
      3. write：A->B，B收到数据包校验后产生并回复ack，A收到B的ack之后生成本端的CQE。
      4. read：本段收到read 的ack，进行数据校验，将数据存放到WQE指定的内存区域，产生CQE。
    2. UD
      1. send：A->B，A发完数据就生成CQE
      2. receive：B收到数据将数据放到用户WQE指定的内存区域，进行校验和数据存放，硬件产生CQE。

  4. CQ与WQ的映射关系

    1. 每个WQ都有一个CQ，一个CQ可以关联绑定多个WQ。WQ中的SQ、RQ可以关联绑定不同的CQ。
    2. 创建QP之前，需要先创建好CQ，创建QP时需要给SQ，RQ分别指定CQ。
    3. 同一个WQ对应产生的CQE在CQ中是保序的，中间可能穿插其他WQ的CQE。

  5. CQC（CQ context）

    1. 内容：CQ的容量大小，当前处理的CQE的序号等等信息

  6. CQN（CQ Number）：CQ的编号（一个节点可以拥有多个CQ，每个节点有自己的一套从0开始编号）

2. 错误类型​

  1. 立即错误：立即停止当前操作，并返回错误给上层用户（例如：在服务类型的QP下下发不支持的操作）
  2. 完成错误：通过CQE将错误信息返回给上层用户（例如：超时没收到ack）
    1. 检测点：
      1. 发送端：本地检测+对端检测回复的ack/如果是UD类型没有ack回复检测，错了直接生成
      2. 接收端：接收端本地检测（回复本地产生CQE，加入到ack中回复给对方）
    2. 常见的完成错误
      1. RC服务类型的SQ完成错误
      2. Local Protection Error 本地保护域错误。本地WQE中指定的数据内存地址的MR不合法，即用户试图使用一片未注册的内存中的数据。
      3. Remote Access Error 远端权限错误。本端没有权限读/写指定的对端内存地址。
      4. Transport Retry Counter Exceeded Error 重传超次错误。对端一直未回复正确的ACK，导致本端多次重传，超过了预设的次数。
      5. RC服务类型的RQ完成错误
      6. Local Access Error 本地访问错误。说明对端试图写入其没有权限写入的内存区域。
      7. Local Length Error 本地长度错误。本地RQ没有足够的空间来接收对端发送的数据。
  3. 异步错误：通过中断事件的方式上报给上层用户（例如：CQE未被取出消耗，CQ溢出，使用最先注册的函数）

3. 用户接口​

  1. 控制面：
    1. Create CQ：创建CQ的软硬件资源（CQ，CQC），
      1. 传入属性：服务类型，CQE数量
    2. Destroy CQ：销毁CQ，释放CQ的全部软硬件资源，销毁后无法通过CQN索引到CQ。
    3. Resize CQ：修改CQ大小，只允许修改规格。
    4. Query CQ：查询CQ大小，用于通知的回调函数指针。
  2. 数据面：（硬件传递消息给软件）
    1. 软件如何感知到CQ中有CQE：
      1. 中断：打断CPU，切换上下文，调用接口实现当前任务执行。Request completion notification
        1. 向系统注册中断，当存放CQE，立即出发中断取出CQE。
      2. 轮询：隔一段时间查看缓冲区是否有数据，有数据处理，没数据去干别的。Poll completion queue
    2. 两种接口：中断+轮询根据负载切换。

2. SRQ​

1.基础概念​

  1. 将所有WQ的RQ绑定到同一个共享的RQ，节省资源。

  2. SQ中下发的任务远多于RQ，SQ中包含send、write、read等多种操作，RQ中只有receive任务。SEND-RECV这一对操作通常都是用于传递控制信息，WRITE和READ才是进行大量远端内存读写操作时的主角，所以自然SQ的使用率是远远高于RQ的。

    1. 需要提前准备足够的内存空间存放足够的RQ CQE，如果一个一个会浪费很多空间、
    2. 否则当WQE不够用时，使用流控技术反压发送端，给接收端时间准备WQE

  3. SRQ内部存放WQE，WQE是多个sge（Scatter/Gather Element）组成的，每个sge是内存地址+长度+密钥组成。（一个sge指向一块连续的内存区域），多个sge合起来表示彼此离散的连续内存块，也称sgl。sge用来指定发送和接收区域。（length：32bit，可以指向4G空间）

  4. SRQC：SRQ Context，包括深度、WQE大小等信息。

  5. SRQN：SRQ Number，每个节点中可能存在多个SRQ，为了标识和区分这些SRQ，每个SRQ都有一个序号，称为SRQN。

  6. SRQ的PD：每个SRQ都必须指定一个自己的PD，可以跟自己关联的QP的PD相同，也可以不同；SRQ之间也可以使用相同的PD。

    1. 收到了Send数据包，那么只有在要访问的MR和SRQ处于同一个PD下，才会正常接收这个数据包，否则会产生立即错误；
    2. 如果收到的是Write/Read，此时比较的仍然是QP和MR的PD。（MR的PD通过va-pa获取，QP记录在QPC中）

2. 异步错误​

  1. SRQ Limit Reached事件：SRQ设置一个水线/阈值，当队列中剩余的WQE数量小于水线时，这个SRQ会就上报一个异步事件。提醒用户“队列中的WQE快用完了，请下发更多WQE以防没有地方接收新的数据”。这个水线/阈值就被称为SRQ Limit，这个上报的事件就被称为SRQ Limit Reached。
  2. 上报异步事件之后，SRQ Limit的值会被硬件重新设置为0（为了防止一直上报异步事件给上层）。当然用户可以不使用这个机制，只需要将SRQ Limit的值设为0即可。

3. 用户接口​

  1. 控制面：
    1. Create SRQ：创建SRQ的软硬件资源（SRQ，SRQC），
      1. 传入属性：服务类型，SRQE深度
    2. Destroy SRQ：销毁SRQ，释放SRQ的全部软硬件资源，销毁后无法通过SRQN索引到SRQ。
    3. Modify SRQ：修改SRQ深度等属性，修改水线。
    4. Query SRQ：查询SRQ水线。
  2. 数据面：（硬件传递消息给软件）
    1. 响应方发起请求：post receive request（receive操作），准备缓冲区，向SRQ填写WQE，指明接收的数据存储的位置。

4. SRQ&RQ​

  1. SRQ只有非错误和错误两种状态：无论是哪种状态下，用户都可以向SRQ中下发WQE，

    1. 在错误状态下，相关联的QP不能从这个SRQ中获得收到的数据。
    2. 在错误状态下，用户也无法查询和修改SRQ的属性。
    3. QP处于错误状态时，可以通过Modify QP来使其回到RESET状态，但是对SRQ来说，只能通过销毁它来退出错误状态。

  2. 对于一个QP来说，RQ和SRQ不能同时使用，两者需选其一，如果对一个已经关联SRQ的QP的RQ下发WQE，那么会返回一个立即错误。

  3. 接收流程对比

    1. RQ

      1. \0. 创建QP。

        1. 通过Post Recv接口，用户分别向QP2和QP3的RQ下发接收WQE，WQE中包含接收到数据后放到哪块内存区域的信息。

        \2. 硬件收到数据。

        \3. 硬件发现是发给QP3的，那么从QP3的RQ中取出WQE1，将接收到的数据放到WQE1指定的内存区域。

        \4. 硬件完成数据存放后，向QP3的RQ关联的CQ3产生一个CQE，上报任务完成信息。

        \5. 用户从CQ3中取出WC（CQE），然后从指定内存区域取走数据。

        \6. 硬件收到数据。

        \7. 硬件发现是发送给QP2的，那么从QP2的RQ中取出WQE1，将接收到的数据放到WQE1指定的内存区域。

        \8. 硬件完成数据存放后，向QP2的RQ关联的CQ2产生一个CQE，上报任务完成信息。

        \9. 用户从CQ2中取出WC（CQE），然后从指定内存区域取走数据。

    2. SRQ

      1. \0. 创建SRQ1，并创建QP2和QP3，都关联到SRQ1上。

        1. 通过Post SRQ Recv接口，用户向SRQ1中下发两个接收WQE，WQE中包含接收到数据后放到哪块内存区域的信息。

        \2. 硬件收到数据。

        \3. 硬件发现是发给QP3的，从SRQ1中取出第一个WQE（现在是WQE1），根据WQE内容存放收到的数据。

        SRQ中的每个WQE是“无主的“，不关联到任何一个QP，硬件按队列顺序依次取出WQE就把数据放到里面了。

        \4. 硬件发现QP3的RQ关联的CQ是CQ3，所以向其中产生一个CQE。

        \5. 用户从CQ3中取出CQE，从指定内存区域取走数据。

        细心地读者可能会问，用户下发WR时，每个WR都指定了一些未来用来存放数据的内存区域。但是SRQ是一个池子，里面每个WQE都指向了不同的若干段内存区域。用户收到某个QP对应的CQ中的WC后如何知道接收到的数据存放到哪里了呢？ WC中其实有wr_id信息，告知用户数据放到哪个WR（WQE）指定的内存区域了，既然WR是用户下发的，用户自然知道其指向的具体位置。

        \6. 硬件收到数据。

        \7. 硬件发现是发给QP2的，从SRQ1中取出第一个WQE（现在是WQE2），根据WQE内容存放收到的数据。

        \8. 硬件发现QP2的RQ关联的CQ是CQ2，所以向其中产生一个CQE。

        \9. 用户从CQ2中取出CQE，从指定内存区域取走数据。

5. WR，WC​

WR，Work Request，工作请求，应用调用硬件API实际上下发WR，在驱动中对应是一个WQE被加入SQ；结束后CQ中CQE被交付到应用，应用收到的是WC。

WR/WC和WQE/CQE是相同的概念在不同层次的实体。

应用-驱动-硬件网卡

6. MR​

MR，Memory Region，RDMA应用划分的专用于RDMA的内存区域，用于存放收发的数据。IB协议中，用户注册好存放数据的内存区域后，调用IB协议下的API调用网卡执行后续操作，RDMA网卡就可以访问这块内存。为了保证这片内存不会被置换（页访问机制，会将某个进程暂时不用的内存内容保存到硬盘，直到进程使用时再搬回内存，这一操作会导致VA-PA映射关系变化），操作系统会提前pin住这块内存，保证网卡可以一直访问直到传输任务结束。

为了确保这块内存可以访问除了先pin住，还需要2个条件，一是需要知道内存的物理地址能找到内存块；二是需要被授权访问，以防传入非法地址。

WQE下发给网卡时的内存的地址是虚拟地址， 通过网卡上的MTT表获取对应的物理地址，然后再去访问存储空间获取数据。（网卡中的MTT表是内存中的一部分，相当于cache，为了便于查找避免反复进入主存翻译地址）

网卡访问内存来自于用户操作，如果用户传入非法地址（系统内存或其他进程使用内存），网卡对内存空间读写会导致信息泄露或内存覆盖。因此必须要对内存进行授权操作，来保证内存地址安全。授权操作指用户在注册MR时需要生成L_key和R_key序列，分别用于访问本端和对端内存空间。

  1. 注册MR实现虚拟地址与物理地址转换
    1. 解决的问题：应用向HCA提供的是虚拟地址。（普通应用，依靠MMU和页表进行VA-PA转换）
    2. 记录VA-PA映射表在内存，RNIC有缓存部分数据。
  2. MR可以控制HCA访问内存的权限
    1. 解决的问题：避免应用提供一个虚假的虚拟地址，导致访问到非法地址造成信息泄露内存覆盖等问题。
    2. 注册MR的动作会产生两把钥匙——L_KEY（Local Key）和R_KEY（Remote Key），用于访问存储空间的密钥。（建联获取对端key和对端存储VA）
  3. MR可以避免换页
    1. 解决的问题：避免传输时缺页替换使得开始注册的VA-PA映射关系失效。
    2. 锁页：即锁定VA-PA的映射关系。也就是说，MR这块内存区域会长期存在于物理内存中不被换页，直到完成通信之后，用户主动注销这片MR。

MR与QP之间没有绑定关系，只要拿到本端的VA和L_key，就可以访问本端结点MR的内容。

7.PD​

PD，Protection Domain，保护域。用于保证RDMA资源间相互隔离。容纳各种资源的容器，PD间的资源彼此隔离无法一起使用。

保证不同的资源，用的key不一样，不是同一个域的QP无法访问别的域的资源，也无法被访问。就算拿到对方域的key，也会因为域不同导致被拒绝。提高安全性、

  1. 资源数值关系：每个节点都至少要有一个PD，每个QP都必须属于一个PD，每个MR也必须属于一个PD。
  2. 表现形式：结构体（记录保护域的信息：MR、QP、AH）
  3. 流程
    1. 通过IB框架的接口创建一个PD，拿到它的指针/句柄。
    2. 创建QP和MR等资源，传入PD句柄，PD信息存储在QP、MR中。
    3. ……
    4. 硬件收发包时，对QP和MR的PD进行校验。
      1. 通过QP对应WQE找到目标VA，通过映射表获取PA，+R_KEY访问MR，找到MR对应的PD和QP本身的PD对应，检测是否一致。一致则访问
  4. PD是本地概念，仅在本端节点内部可见。（对端节点不可见）。MR本端和对端都可见。

8.GID​

GID，Global Identifier，全局ID，用于区分节点。

9.AH​

AH，Address Handle，地址句柄，地址：远端节点的信息集合（包括GID、端口号）。地址句柄为这个信息集合的指针。在UD服务通信时，需要为每一个需要通信的对端节点创建一个AH，被本端多个QP共同使用。

  1. 流程

    1. 使用API创建AH，被驱动放入安全区域并返回句柄
    2. 下发请求WQE传入句柄

  2. AH的作用和意义

    1. 保证目的地址可用，提高效率：保证创建的AH是有效的
    2. 向用户隐藏底层地址细节：只需要用户传入gid，端口，速率等信息就可以创建，mac等信息内核解析获取无需用户参与。
    3. 使用PD对目的地址进行管理：实现对所有QP可达目的地进行隔离和管理。

10. MW​

MW，Memory Window，内存窗口，一种由用户申请的，用于让远端节点访问本端内存区域的RDMA资源。每个MW都会绑定（称为bind）在一个已经注册的MR上，但是它相比于MR可以提供更灵活的权限控制。MW可以粗略理解为是MR的子集，一个MR上可以划分出很多MW，每个MW都可以设置自己的权限。

1.内存访问权限控制​

1）MR/MW的权限配置（有权利操作）​

权限，指的是本端/对端节点，对于本端内存的读/写权限，它们两两组合形成了四种权限：（除此之外还有Atomic权限）

本端对端
读Local ReadRemote Read
写Local WriteRemote Write
  1. 本地读（Local Read）：用户必须赋予MR/MW的权限（至少要本地可以访问，不访问没意义）
  2. 远端写（Remote Write）/（Remote Atomic）：配置远端写，必须配置本地写（Local Write）。

2）Memory Key（保证是合法操作）​

访问MR的钥匙，Key是一串数字，由两部分组成：24bit的Index以及8bit的Key：

  1. Index用于HCA快速索引到本地的虚拟-物理地址转换表等MR相关的信息。

  2. key用于校验整个字段的合法性，以防止未授权的用户任意传递Index。

  3. key分类

    1. Local Key ：L_Key
      1. 关联到一个MR上，用于HCA访问本端内存。当本端的某个进程试图使用一个已经注册的MR的内存时，HCA会校验其传递的L_Key。并且利用L_Key中的索引查找地址转换表，把虚拟地址翻译成物理地址然后访问内存。
      2. 网卡如果访问本地内存，sge描述内存块，其中的key就是L_Key
    2. Remote Key ：R_Key
      1. 联到一个MR或者MW上，用于远端节点访问本端内存。当远端节点试图访问本端的内存时，一方面本端的HCA会校验R_Key是否合法，另一方面会利用R_Key中的索引查地址转换表，把虚拟地址翻译成物理地址然后访问内存。
      2. RDMA操作（即Write/Read/Atomic），用户都要在WR中携带远端内存区域的R_Key。

2.MW出现的原因/必要性​

目标：更灵活的控制内存的远程访问权限。

  1. MR修改MR信息（修改选线，更新key）需要先destroy，然后重新resgister，需要重新陷入内核，耗时长。
  2. MW创建好，可以通过用户态下发WR到硬件，动态绑定到已经注册的MR，同时设置或更改权限，速度更快。

3.MW和MR权限的关系​

  1. 注册MR：配置权限
  2. MW绑定到MR：配置权限
    1. 给MW配置远程写或者远程原子操作（Atomic）权限，那么它绑定到的MR必须有本地写权限。（远程的MW如何绑定权限，远端操作？这个MW是用于远端的？是本地创建还是远端创建？）
    2. 其他情况下两者权限互不干扰，远端用户用MW，就要遵循MW的权限配置；远端用户用MR，就要遵循MR的权限配置。

4. 用户接口​

1）控制路径：增删查，不可以修改​

  1. 创建——Allocate MW：创建MW相关软件结构，产生一个Memory Window的句柄，用于指代该MW。
  2. 删除——Deallocate MW：销毁相关资源。
  3. 查询——Query MW：查询MW的信息，包括R_Key及其状态、MW类型以及PD等。

2）数据路径​

  1. 绑定——Bind

    1. 将一个MW“关联”到一个已经注册的MR的指定范围上，并配置一定的读写权限。绑定的结果会产生一个R_key，用户可以把这个R_Key传递给远端节点用于远程访问。

    2. 一个MW可以被多次绑定，一个MR上也可以绑定多个MW。

    3. 如果一个MR还有被绑定的MW，那么这个MR是不能被取消注册的。

    4. Bind方式：

      1. 调用Post Send接口下发Bind MW WR。（Type 2的MW）

        1. 用户通过post send接口（比如ibv_post_send()）下发一个WR到SQ中，这个WR的操作类型（比如SEND/RDMA WRITE/RDMA READ）被指定为BIND MW。
        2. WR中还携带有权限和要绑定到的MR的范围信息。
        3. 与其他WR不同，下发Bind MW的WR之后，硬件并不会发送任何数据包，而是将MW绑定到了指定MR上。

      2. 是调用Bind MW接口。（Type 1的MW）

        1. 独立接口：实际实现方式为在Post Send Bind MW WR外面又封装了一层。用户传入MW绑定的相关信息，包括权限及要绑定的MR的信息，驱动程序负责组装和下发WR到硬件中。该接口成功后，会将新生成的R_Key返回给用户。

  2. 无效化——Invalidate（作用于Type 2的MW）

    1. 用户通过下发一个带有Invalidate操作码的WR到硬件而使一个R_Key无效的操作。
      1. 作用对象是R_Key，远端用户无法再使用R_Key访问对应MW，MW存在后续可以生成新的R_Key供远端使用。
    2. 按操作发起方分类
      1. Local Invalidate 本地无效操作。（远端用户无法访问本地）
        1. 上层用户如果想在不回收MW资源的情况下，收回某个远端的用户的R_Key的权限。就可以下发一个Local Invalidate操作到SQ中，硬件收到之后会对相应的MR的配置进行修改。
        2. 成功执行之后，如果持有这个R_Key的远端用户想要对MW进行RDMA操作，将会被本地的硬件拒绝并返回错误。
        3. 不会发到链路上。
      2. Remote Invalidate 远端无效操作。（远端用户说，我不想访问你）
        1. 当一个远端用户不再使用一个R_Key之后，可以主动发送消息，让本端回收这个R_Key。远端用户下发一个带有此操作码的WR到SQ中，其硬件收到后，将会组装一个报文并发送到本端。本端硬件收到远端的Remote Invalidate操作之后，将会把对应的R_Key置为不可用状态。同Local Invalidate一样，此后对端将无法使用这个R_Key对对应的MW进行RDMA操作。

5.MW分类​

1）Type 1​

  1. Type 1的MW通过PD和一个QP关联，不会绑定到一个QP上，所以也不会影响销毁同一个PD下的QP。
  2. Type 1的MW的key由驱动和硬件分配，而不是上层用户。因此用户无法发起失效操作。
  3. 重新绑定该MW，之前的R_Key就会失效，会自动分配新的R_Key的key域段。
  4. 想要使一个MW不再绑定到任何MR，但是又想保留相关的资源而不是销毁这个MW，那么可以通过调用Bind MW接口，并将MW长度设置为0来实现。
  5. 多个MW绑定到同一个MR时，范围相互覆盖，到底谁可以访问？（最后绑定的？还是都可以使用修改）

2）Type 2​

  1. R_Key的key域段由用户掌握，即用户想怎么分配就怎么分配。
  2. 通过Post Send Bind MW WR操作来进行绑定，这个过程并不会返回R_Key。用户必须记住Allocate MW时的index，并且和其选择的8 bit key组成R_Key并发送给对端。
  3. 可以使用无效操作使key无效。然后可以分配新的Key。
  4. 不同MW可以绑定到同一个MR，范围相互覆盖。根据绑定关系可以分为：
    1. Type 2A：通过QPN和一个QP关联，也就是说远端访问这个MW范围内的内存时候，除了R_Key之外，还必须指定正确的QPN。如果一个QP上还有绑定的Type 2A的MW，那么这个QP不可以被销毁。
    2. Type 2B：通过QPN和PD与一个QP关联，比Type 2A多了个PD的校验，即远端通过RDMA操作访问MW的内存时，除了QPN要正确之外，其指定的本端QP的PD要与绑定这个MW时的PD相同。另外，与Type 2A不同，QP如果还有Type 2B MW绑定关系时是可以被销毁的。

HCA必须实现Type 1的MW，另外可以仅选择实现Type 2A和2B中的一种。Type 1和Type 2的MW可以同时关联到同一个MR上。
