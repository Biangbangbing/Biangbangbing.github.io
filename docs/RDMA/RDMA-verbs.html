5. RDMA-verbs

1.verbs是什么​

  1. IB规范所描述的一组抽象定义，规定了各厂商的软硬件在各种Verbs下应该执行的动作或者表现出的行为，IB规范并未规定如何编程实现这些Verbs，在这种含义下，Verbs是与操作系统无关的。

    1. 规定支持的接口，规定需要实现的内容，规定输入输出但不规定具体实现。

  2. 由OpenFabrics推动实现的一组RDMA应用编程接口（API）。和运行的操作系统相关。Verbs API有Linux版本以及Windows版本（Windows版很久没有更新了）。

    1. 软件实现

      1. #include <infiniband/verbs.h>
        struct ibv_qp *ibv_create_qp(struct ibv_pd *pd, struct ibv_qp_init_attr *qp_init_attr); 

        struct ibv_qp_init_attr {
        struct ibv_cq          *send_cq;        /* CQ to be associated with the Send Queue (SQ) */
        struct ibv_cq          *recv_cq;        /* CQ to be associated with the Receive Queue (RQ) */
        struct ibv_srq         *srq;            /* SRQ handle if QP is to be associated with an SRQ, otherwise NULL */
        struct ibv_qp_cap       cap;            /* QP capabilities */
        enum ibv_qp_type        qp_type;        /* QP Transport Service Type: IBV_QPT_RC, IBV_QPT_UC, or IBV_QPT_UD */
        ...
        };

​

2.相关名词解释​

1. RDMA-core（用户态代码+驱动）​

开源RDMA用户态软件协议栈，包含用户态框架、各厂商用户态驱动、API帮助手册以及开发自测试工具等。在github上维护，用户态的Verbs API就是rdma-core实现的。

2.kernel RDMA subsystem（内核）​

开源的Linux内核中的RDMA子系统，包含RDMA内核框架及各厂商的驱动。

RDMA子系统跟随Linux维护，是内核的的一部分。一方面提供内核态的Verbs API，一方面负责对接用户态的接口。

3.OFED​

OpenFabrics Enterprise Distribution，是一个开源软件包集合，其中包含内核框架和驱动、用户框架和驱动、以及各种中间件、测试工具和API文档。

开源OFED：由OFA组织负责开发、发布和维护，它会定期从rdma-core和内核的RDMA子系统取软件版本，并对各商用OS发行版进行适配。除了协议栈和驱动外，还包含了perftest等测试工具。平均每连个月都有一个版本，OFED会定期从两个社区中取得代码，进行功能和兼容性测试后发布版本，时间跨度较大，以年为单位计。

厂商定制OFED：厂商也会提供定制版本的OFED软件包，比如华为的HW_OFED和Mellanox的MLNX_OFED。这些定制版本基于开源OFED开发，由厂商自己测试和维护，会在开源软件包基础上提供私有的增强特性，并附上自己的配置、测试工具等。

4.verbs-api​

一组RDMA应用使用RDMA服务的最基本软件接口。直接基于这组API编写应用或者基于在Verbs API上又封装了一层接口的各种中间件编写。

向用户提供的包含的RDMA功能

  1. 注册MR、
  2. 创建QP、
  3. Post Send、
  4. Poll CQ……

1）IB_VERBS（最基础的编程接口）​

  1. ibv_xx（用户态）
    1. ibv_create_qp() 用于创建QP
    2. ibv_post_send() 用于下发Send WR
    3. ibv_poll_cq() 用于从CQ中轮询CQE
  2. ib_xx（内核态）

2）RDMA_CM​

  1. CMA（Connection Management Abstraction）
    1. 在Verbs API基础上实现的，用于CM建链并交换信息的一组接口。CM建链借鉴了Socket的流程和API，底层是基于QP实现的，从用户的角度来看，是在通过QP交换之后数据交换所需要的QPN，Key等信息。
      1. rdma_listen()用于监听链路上的CM建链请求。
      2. rdma_connect()用于确认CM连接。
  2. CM VERBS
    1. 用于数据交换，相当于在verbs API上又封装了一套数据交换接口。
      1. rdma_post_read()可以直接下发RDMA READ操作的WR，而不像ibv_post_send()，需要在参数中指定操作类型为READ。
      2. rdma_post_ud_send()可以直接传入远端QPN，指向远端的AH，本地缓冲区指针等信息触发一次UD SEND操作。
    2. 需要配合CMA管理的链路使用，不能配合Verbs API使用。

3）MAD接口……​

软件栈中的Verbs API具体实现和IB规范中的描述并不是完全一致的。IB规范迭代较慢，而软件栈几乎每天都有变化，所以编写应用或者驱动程序时，应以软件栈API文档中的描述为准。

3. verbs-api（用户态/内核）​

1）设计的意义​

  1. 可以使得RDMA应用编写应用程序。
  2. Verbs API支持IB/iWARP/RoCE三大RDMA协议，通过统一接口，让同一份RDMA程序程序可以无视底层的硬件和链路差异运行在不同的环境中。

2）包含的内容​

  1. 控制面

    1. 设备管理

      1. *device_list*ibv_get_device_list() 用户获取可用的RDMA设备列表，会返回一组可用设备的指针。
      2. *device_context*ibv_open_device(device) 打开一个可用的RDMA设备，返回其上下文指针（这个指针会在以后用来对这个设备进行各种操作）。
      3. device_attr, errno ibv_query_device(device_context*) 查询一个设备的属性/能力，比如其支持的最大QP，CQ数量等。返回设备的属性结构体指针，以及错误码。

    2. 资源的创建，查询，修改和销毁：

      1. *pd*ibv_alloc_pd(device_context) 申请PD。该函数会返回一个PD的指针。
      1. *mr*ibv_reg_mr(pd, addr, length, access_flag) 注册MR。用户传入要注册的内存的起始地址和长度，以及这个MR将要从属的PD和它的访问权限（本地读/写，远端读/写等），返回一个MR的指针给用户。
      1. cq ibv_create_cq(device_context, cqe_depth, ...) 创建CQ。用户传入CQ的最小深度（驱动实际申请的可能比这个值大），然后该函数返回CQ的指针。
      1. *qp*ibv_create_qp(pd, qp_init_attr) 创建QP。用户传入PD和一组属性（包括RQ和SQ绑定到的CQ、QP绑定的SRQ、QP的能力、QP类型等），向用户返回QP的指针。
      1. *errno*ibv_modiy_qp(qp, attr, attr_mask) 修改QP。用户传入QP的指针，以及表示要修改的属性的掩码和要修改值。修改的内容可以是QP状态、对端QPN、QP能力、端口号和重传次数等等。如果失败，该函数会返回错误码。Modify QP最重要的作用是让QP在不同的状态间迁移，完成RST-->INIT-->RTR-->RTS的状态机转移后才具备下发Send WR的能力。也可用来将QP切换到ERROR状态。
      1. *errno*ibv_destroy_qp(qp) 销毁QP。即销毁QP相关的软件资源。其他的资源也都有类似的销毁接口。

    • 中断处理：

      • *event_info, errno*ibv_get_async_event(device_context) 从事件队列中获取一个异步事件，返回异步事件的信息（事件来源，事件类型等）以及错误码。

    • 连接管理

      1. rdma_xxx()

  2. 数据面

    1. 下发WR：*bad_wr, errno*ibv_post_send(qp, wr)； bad_wr, errno ibv_post_recv(qp, wr)；
      1. 向一个QP下发一个Send WR，参数wr是一个结构体，包含了WR的所有信息。包括wr_id、sge数量、操作码（SEND/WRITE/READ等以及更细分的类型）。
      2. WR的结构会根据服务类型和操作类型有所差异，比如RC服务的WRITE和READ操作的WR会包含远端内存地址和R_Key，UD服务类型会包含AH，远端QPN和Q_Key等。
      3. WR经由驱动进一步处理后，会转化成WQE下发给硬件。
      4. 出错之后，该接口会返回出错的WR的指针以及错误码。
    2. 获取WC：num, wc ibv_poll_cq(cq, max_num)
      1. 从完成队列CQ中轮询CQE，用户需要提前准备好内存来存放WC，并传入可以接收多少个WC。该接口会返回一组WC结构体（其内容包括wr_id，状态，操作码，QPN等信息）以及WC的数量。

4. 用户态&内核态交互配合​

RDMA减少了对内核的调用，在大量数据发送时绕过内核，降低了内核开销。哪些API依赖于内核RDMA子系统（包括驱动），为什么需要依赖内核，以及用户态和内核是如何交互的。

1）verbs分类​

  1. 特权用户：直接访问OS内部数据，控制RDMA硬件=》全部verbs
  2. 用户态用户：依赖代理访问OS数据=》部分verbs
  3. 实现必要性：Mandatory：必须支持实现；
    1. 用于数据交互绑定MW、AH：用户态
    2. 其他操作：特权用户

2）软件协议栈架构（OFED：内核+用户）​

  1. 用户空间

    1. 应用Application：各种RDMA应用程序（比如perftest）、中间件（比如UCX）等。
    2. libibverbs.so：RDMA软件栈用户态核心动态链接库
      1. 实现并且向上层应用提供各种Verbs API
      2. 在各种Verbs API的逻辑中调用到各厂商驱动注册的钩子函数
      3. 提供进入内核态的接口
    3. libmlx5.so：（Mellanox ConnectX-5）网卡的用户态驱动，也是个动态链接库，实现厂商的驱动逻辑。

  2. 内核

    1. 中间交互模块
      1. 负责通过ABI来处理用户态的系统调用请求：用户态verbs陷入内核，需要通过这一层的ib_uverbs模块来解析命令；另外右侧的xxx.ko指的是使用内核verbs接口（比如ib_post_send）的上层应用程序所需要的处理系统调用的自定义模块。
    2. ib_core.ko：内核RDMA子系统核心模块
      1. 向使用内核态Verbs的应用程序提供内核态Verbs API
      2. 在各种Verbs API的逻辑中调用到各厂商驱动注册的钩子函数
      3. 管理各种RDMA资源，为用户态提供服务
    3. mlx5_ib.ko：网卡的内核态驱动模块，负责直接和硬件交互。
    4. 硬件：网卡

  3. 通信路径：

    1. 红色虚线为界分左右来看这张图：左侧是用户态应用程序的层次结构，右侧为内核态应用（通过中间模块简介使用内核verbs API的应用）程序的层次结构。其中用户态应用又分为左右两条路，左边绕过内
    2. 核的是指数据路径，右边需要通过内核的是指控制路径。

3）陷入内核态的必要​

  1. 用户态是不安全的，有些资源不能暴露给用户态修改：避免RDMA资源被用户恶意篡改
  2. 需要建立虚拟地址到物理地址的静态映射：在注册MR的过程中，内核驱动会为硬件建立地址映射表。而为了防止换页导致的虚拟-物理地址映射关系发生改变，内核驱动会触发pin的动作，即固定这个映射关系。发数据时避免了反复用户和内核的上下文切换。

4）内核和用户态如何交流​

  1. 控制路径：

    1. write系统调用对/dev/infiniband/uverbsN字符设备文件进行操作实现两者信息交流。
    2. ioctl()系统调用

  2. API：Application Programming Interface，程序之间的编程接口。Verbs接口就是一套API。

  3. ABI：Application Binary Interface，应用程序间的二进制接口。RDMA软件栈架构图中的Userspace和Kernel之间的uverbs接口就是一种ABI

    1. 定义了运行时的程序之间交流的格式，比如参数以什么形式传递（分别写到指定的寄存器/使用栈）、以什么格式传递以及返回值放到哪里等。用户态传输cmd给内核，内核回复resp消息。

    2. uverbs ABI接口来保证不同版本的用户态和内核态之间的兼容性，即某个版本的用户态库，可以直接运行在各种版本的内核上。

    3. 整套用户态和内核的交互机制都是由内核的ib_uverbs.ko和用户态的libibverbs.so相配合实现的。

      • 命令码：告诉内核态当前陷入内核态想要执行的操作
      • 公共域段：所有厂商的创建QP动作都需要从用户态传递到内核态的参数
      • 驱动自定义域段：各个厂商自定义的需要传递到内核的参数

      • 公共域段：所有厂商在内核创建完QP之后，需要返回给用户态的参数
      • 驱动自定义域段：各个厂商的自定义返回参数

5. 调用verbs整体流程​

1）需要陷入内核​

  1. ibv_open_device()：打开设备

    1. 创建设备上下文结构device_context：软件角度的设备实体。

    2. 映射PCIe BAR空间，让用户获取到Doorbell的地址：让用户能够直接读写网卡的某些寄存器来实现和硬件的交互。（包括doorbell寄存器，当准备好WR之后向该寄存器写入数据，硬件就将WQE取走）

    3. 挂载回调函数到IB框架：IB框架开放钩子函数，不同硬件型号写对应的函数，使得其能调用不同硬件的函数。

    4. 查询设备能力：获知当前硬件支持的功能、规格等信息。eg：支持创建多少个QP，多少个CQ等。

  2. ibv_reg_mr()：注册MR

    1. pin住内存

    2. 建立VA-PA映射表

  3. ibv_create_qp()：创建QP

    1. 校验并根据硬件能力修正QP参数

    2. 创建QP的相关资源：QPC、QPN等

    3. 申请QP缓冲区：SQ、RQ WQE区域，创建完成驱动会把QP的基地址告诉硬件。

2）不需要陷入内核​

  1. ibv_post_send()
    1. 从QP Buffer中获得下一个WQE的内存首地址（ibv_create_qp()中申请的）
    2. 根据与硬件约定好的结构，解析WR中的内容填写到WQE中
    3. 数据区域通过sge指定，sge指向的内存位于MR中（ibv_reg_mr()中注册的）
    4. 填写完毕，敲Doorbell告知硬件（地址是ibv_open_device()中映射得到的）
    5. 硬件从QP Buffer中取出WQE并解析其内容
    6. 硬件通过映射表（ibv_reg_mr()中建立的），将存放数据的虚拟地址转换成物理地址，取出数据
    7. 硬件组包、发送数据

6.RDMA建连​

建立连接之后，本端和对端才可以开始通信，是正式通信前必须进行的准备工作。

1.为什么必须要建连​

  1. 当节点A想要向节点B之间建立RC服务，进行数据传输，在下发WQE之后需要知道向谁发送数据。
    1. 目的地的信息存储在QPC上（通过Modify QP接口实现）
    2. 必要协商准备，掌握彼此信息（r_key）
  2. 当节点A的一个WQE想要和节点B建立UD服务，如何获取对端信息，
    1. 需要建连获取对端信息，下发WR时通过WR指定
  3. RDMA网卡通过QPC或者WR组件完整报文，二者中包含的对端信息通过建连获取

2.建连方式（用户接口区分）​

  1. Socket API
  2. CM（Communication Manager/Management）
    1. Inifinband/RoCE：IB传输层 + IB规范所描述的CM协议
    2. iWARP：TCP + IETF RFC 5044/6581
  3. 如果直接知道，也可以直接写对端信息……

3.socket API建连（带外建连）​

（API以下都是硬件实现的）​

1）概述​

  1. 是基于TCP/IP协议栈的一个中间层，为用户提供了一组标准编程接口。通过Socket API，用户可以在节点之间通过TCP/IP协议进行数据交互。
  2. 使用socket API建连要求两个节点之间必须要建立TCPIP连接，通过这条连接交互双方QP信息。双方必须支持TCPIP协议。
    1. Infiniband/RoCE v1的设备：不支持TCPIP【不可以】（如果两者之间还有以太网卡，也可以）
    2. iWARP：TCP/IP被封装到了CM方式里。【直接用CM】
    3. RoCE v2：支持【可以】

2）建立Socket连接​

  1. 按照一定流程调用socket API，实现TCPIP三次握手四次挥手进行通信。（调用内核的TCP协议实现+网卡的IP层）

3）通过Socket连接交换信息​

  1. 创建好socket之后，需要编写交互逻辑【用户层完成】

  2. 必须要交换的信息

    1. gid：全局ID，是Infiniband网络层（Network Layer）的地址，用于在跨子网时做路由。在IB协议中相当于IP地址。【物理节点？进程？】
      1. 即便RoCEv2中有IP层，RDMA用户仍然使用gid指定本端和对端地址。
      2. 硬件知道的对端地址信息：目标GID、目的MAC、VLAN等，通过用户传入的DGID（Destination GID）获取。
        1. 驱动程序会将GID转换为IP地址（有转换关系）
        2. 通过网络侧的邻居表获取MAC地址和VLAN ID
    2. QPN：一个节点（物理节点？进程？）本地某个QP的唯一编号。
      1. 通信的基本单位是QP：通过gid+QPN确定唯一QP。
    3. VA：通过RDMA技术进行通信的进程的某个虚拟地址，这个虚拟地址上注册了MR，并设置了远端直接读/写的权限。
    4. R_Key：在单边操作中，校验远端是否对于指定的MR具有读写权限。A收到B的VA + R_Key，A可以对B的一部分内存进行安全读写操作。
    5. Q_Key：只在UD服务下使用的key。避免接收端的RQ WQE被恶意用户不断发送send消耗掉而无法处理正常的send消息。因此在建连时传输Q_Key，后续发送消息时，携带Q_Key，接收报文时校验通过接收，否则丢弃。
    6. 还有一些信息PSN、Path MTU等等可以交换，在对应操作成功获取这些信息之后进行交换。
      1. RDMAmojo上面的这篇文章

4.CM建连【】​

cm，可以指协议，也可以指RDMA网络中的一个管理角色，还可以指编程接口（API）。

1）概述（CM的多重含义）​

  1. 通信管理协议：Communication Management Protocol，通信管理协议。它指的是一种建立于Infiniband/RoCE协议基础之上的建链方式。也是通过报文的多次往返来建立连接的，同时它也规定了断链的方式。

  2. 通信管理器：CM作为Infiniband/RoCE通信系统中的角色时，全称为Communication Manager，即通信管理器。这是一个比较抽象的概念，它的作用是建立和维护两个节点间的连接。虽然抽象，但是它是有“实体”的，RDMA软件协议栈中实现了CM管理器的功能。

  3. CM编程接口：作为Infiniband/RoCE/iWARP的用户编程接口时，全称也是Communication Manager，即通信管理接口。CM接口之于CM协议，就如Socket接口之于TCP协议，其调用流程也和Socket非常相似，CM API是基于RDMA而非传统以太网实现的类Socket接口。

2）为什么需要CM​

  1. Infiniband协议没有Socket这种通道来在双方交换业务数据前传递必要的信息，比如QPN、Virtual Address和Remote Key等。需要一种不依赖于以太网的QP间建联方式，所以会有CM协议和通信管理器的存在。
  2. 建连由用户发起，因此需要对应的用户编程接口CM API。
  3. CM是基于Infiniband传输层实现的，诞生于RoCE之前，RoCE v1/v2使用IB传输层，自产生开始就天然支持CM建链。RoCE底层是基于以太网的，一般支持RoCE v2的网卡都会支持TCP/IP协议，因此大多数RoCE网卡都可以支持Socket和CM两种建链方式。
  4. iWARP自成体系，它通过IETF的RFC 5044和RFC 6581（详情见“iWARP”一文）对于建链方式做出了规定。iWARP的做法是规定了一套基于在TCP之上的MPA层的交互流程，与CM协议毫不相关。并且由于在TCP层上面加了一层，往往由各个厂商自己在驱动程序中进行差异化实现，所以也无法使用标准Socket API。
  5. iWARP后来逐渐和Infiniband/RoCE统一了软件接口和软件栈，这其中就包括CM API。它虽然使用着CM API，但是底层还是按照其RFC中的规定所实现的。

3）协议分层​

  • RoCE/Infiniband：CM和MAD层是软件实现的；
  • iWARP：*建链时使用的MPA及以下各层？*，也是软件实现的。

  1. MPA层：Marker PDU Aligned framing，iWARP协议族的最底层，向下基于TCP层，向上为DDP层提供服务

  2. MAD层：Management Datagram，即管理数据报。MAD层就是基于IB传输层的UD服务类型实现的。

    1. 作为中间层向上支持GS（General Services）和SM（Subnet Management）两种服务。
      1. SM只用于Infiniband网络，
      2. General Service包括性能管理、设备管理、应用管理以及CM连接管理。
    2. 内核协议栈创建QP0以及QP1：用于收发MAD层管理报文，无法被用户使用。
      1. 软件协议栈的QP类型分别是：SMI（Subnet Management Interface）和GSI（General Services Interface）【本质是UD类型的QP，只是权限特殊，起了专有类型名】
        1. 使用UD类型：可以发给任意节点，不需要每个节点都来一对RC QP，减少内存资源消耗。
        2. 所有的节点只需要建立一个专门用于CM的UD（GSI） QP
      2. 指定QPN为1，指定Q_Key：0x8001_0000。（最高位为1的Queue Key都是特权Key，普通的用户无法使用，保证了CM只能由内核态协议栈来管理。）

  3. CM层：

    1. 实现CM协议
    2. 软件完成功能：
      1. 为用户提供类似Verbs API的CM API，处理用户对API的调用。
      2. 根据网卡使用的协议来组装或者解析报文。
    3. 发送：
      1. RoCE/Infiniband协议：组装CM协议报文，下发给MAD，通过GSI QP发送建连报文
      2. iWARP协议：调用各个厂商注册的回调函数组装MPA层的报文，厂商的驱动最终会调用Socket接口，由内核协议栈继续组装TCP/IP层的报文并发送。
    4. 接收：
      1. RoCE/Infiniband协议：解析CM协议报文
      2. iWARP协议：调用网卡驱动注册的回调函数对MPA报文进行解析。

4）CM协议​

  1. RC 类型QP使用CM进行建连
    1. RC服务类型需要：建连——数据交互——断连全流程
    2. 建连（三次握手）【任意环节出错会给对端发出REJ消息。】
      1. client发起请求REQ（Request）
        1. 携带连接参数：要连接的QP的QPN（这个QP是在CM建链流程中通过CM API创建的，下文会介绍）、起始PSN、重传次数上限等等。
      2. server监听到请求——CM层进行校验记录——回复REP（REPLY）
        1. 表明接受请求，回复携带连接参数：QPN、起始PSN等
      3. client收到REP回复，对其中内容校验记录，发送RTU（Ready To Use）
        1. 表明同意参数。
        2. 之后就开始发送数据。server收到rtu之后也可以开始发送数据。
    3. 断连（四次挥手）【谁先发起都可以】
      1. 如果client发起请求断连DREQ（Disconnect Request）
        1. 携带着指定连接的ID以及QPN等信息
      2. server收到DREQ——验证通过——回复DREP（Disconnect Reply）
      3. Server端发送DREQ
      4. Client端收到DREQ——校验通过——回复DREP
        1. 双方都收到对方的rep之后就可以销毁和CM有关的资源。
  2. UD 类型QP使用CM进行建连
    1. UD服务类型：获取对方信息——数据交互
    2. 建连【SIDR，Service ID Resolution Protocol】
      1. client发起发送SIDR_REQ（SIDR Request）
        1. 携带一个Service ID字段（需要server提供的服务）
      2. server收到消息——校验——回复SIDR_REP（SIDR Reply）
        1. 携带一个和Service ID对应的可用QP的QPN以及Queue Key
      3. client收到回复，利用数据发送消息
    3. Service ID和QPN的对应关系可自行定义；
    4. server不知道client的QPN，如果server有发送数据的需要，可以通过其他交互流程知道（payload携带/send imme）
